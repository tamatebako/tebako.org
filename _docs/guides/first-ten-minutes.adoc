== The five binaries.

The release publishes one asset per binary per platform, and **the asset
names carry the version while the binaries expect the bare names**. Rename on
download — skipping this stops `tebako install` at the shim step, after it has
already downloaded the payload:

[source,console]
----
$ mkdir -p ~/.local/bin && cd ~/.local/bin
$ for b in tebako tebako-pkg tfs tebako-bootstrap tebako-shim; do
    curl -fsSLO "https://github.com/tamatebako/tebako/releases/download/v<ver>/$b-<ver>-macos-arm64"
    mv "$b-<ver>-macos-arm64" "$b"
  done
$ chmod 0755 tebako tebako-pkg tfs tebako-bootstrap tebako-shim
$ ./tebako --version
Tebako executable packager version <ver>
----

`tebako-shim` is the fifth binary and the one a hand download forgets: it is
the dispatcher every installed shim links to. Homebrew and the shell installer
put all five in place, with their names, for you.

== A first payload.

`tebako setup` seeds the official registry. There is nothing to add for the
first command, and adding a second registry that carries the same payload name
turns a bare `install` into an ambiguity error — the message names both
registries and asks for the full reference.

[source,console]
----
$ tebako setup
fetching registry tfs:github:tebako-packages/registry
seeded the official registry tfs:github:tebako-packages/registry (16 payload(s))
$ tebako install hello
resolving hello
└ toolkit hello 2.12 — fetching
installed payload hello@2.12 (28.3 KB)
shim ~/.tebako/shims/hello
$ tebako-shim install-shell    # once per machine — puts ~/.tebako/shims on PATH
$ hello
Hello, world!
----

Open a new shell after `install-shell`, or call the shim by path
(`~/.tebako/shims/hello`) until you do: it writes the PATH line into your
shell's startup file, which the current shell has already read.

== A payload that carries a runtime.

A payload of kind `runtime` provides an interpreter, and the payloads that need
one declare it as a dependency. The first run fetches the runtime — once per
machine — verifies it, and caches it; every later run starts from the cache.

[source,console]
----
$ tebako install hello-ruby
$ hello-ruby
fetching runtime ruby@4.0.7;tebako=0.17.3;image: 2 artifacts, 19.2 MB total
… lazy: seeding on demand, sealing in background
Hello from tebako (ruby 4.0.7, arm64-darwin23)
----

The store keeps the runtime under `~/.tebako/runtimes` and never extracts it
into a system path; `tebako doctor` names anything that has drifted, with its
remedy.

== Press your own.

A directory with one root script is a project. `tebako press` detects it,
resolves the runtime from the registry — the same pair `install` would pick —
and writes a single executable that carries your code and mounts it.

[source,console]
----
$ mkdir hello && cd hello
$ echo 'puts "hello from a pressed app (ruby #{RUBY_VERSION})"' > main.rb
$ tebako press -r . -e main.rb -o ../hello.bin
   Ruby version:             '4.0.7'
Created tebako package at "…/hello.bin"
$ ../hello.bin
hello from a pressed app (ruby 4.0.7)
----

Write the package **outside** the project root. Pressing in place works — the
tool says so, then warns — because each press would image the previous package
sitting beside the source, which is how old versions end up nested inside new
ones.

Press it again after an edit: the packaging environment is reused, so the loop
is a few seconds rather than a download.
