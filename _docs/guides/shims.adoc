== The shim directory on PATH, once.

[source,console]
----
$ tebako-shim install-shell            # detects your shell
$ tebako-shim install-shell --shell zsh  # or name it: bash|zsh|fish|csh
----

`install-shell` prepends `~/.tebako/shims` to PATH inside a managed block in the shell startup file — idempotent, and removed by `tebako-shim uninstall-shell`. On Windows the shim directory goes on the user PATH in the registry (HKEY_CURRENT_USER, HKCU). Open a new shell afterwards.

Prepend is the default because a shim just installed should answer. Where a version manager (mise, rbenv) or a system tool must keep the lead, `--position append` (tebako 2.8.77) puts the shim directory last on PATH instead, and tebako then answers only for the names nothing else provides:

[source,console]
----
$ tebako-shim install-shell --position append
----

Re-running with the other position rewrites the managed block in place; the rest of the startup file is never touched.

== Where shims come from.

A command passes through three tiers before it answers on PATH, and each tier has its own owner. The payload author declares the complete inventory (the *declared* tier — the only set `tebako run <name>` resolves against) and chooses which of those commands claim a PATH name by default (the *default-active* tier, the manifest's `active:` key). The install decides what actually links on this machine (the *linked* tier): the default is the author's active set, and `tebako install <name> --only-shims a,b` or `--no-shims` (tebako 2.8.77) narrows it. A linked command can always be unlinked later with `tebako shim hide`, and every declared command — linked or not — remains dispatchable through `tebako run`.

`tebako uninstall <name>` removes the shims and the cache entry. There is no `tebako shim add/remove/list` — the read-side verb is `tebako-shim list`.

Two classes of shim share the directory. A *payload shim* dispatches to a packaged payload, which is the class the rest of this guide describes. A *runtime-own shim* dispatches to an engine's own tool with no payload in between, and `tebako install <engine>[:<command>]` creates it: the bare form registers the interpreter's own name, and the colon form registers the declared command's name.

[source,console]
----
$ tebako install node:node
node 24.22.0 is already installed (~/.tebako/runtimes/node-24.22.0-2.8.49-macos-arm64)
  shim ~/.tebako/shims/node
$ node --version
v24.22.0
----

The claims live in `~/.tebako/shims/.runtime-own.yaml`, a map from each registered name to the engine and the entry token it boots. `tebako-shim list` reports them beside the payload shims and marks them `[runtime-own]`. When a payload provides a name that a runtime-own claim also carries, the payload's name wins on every dispatch, and a later payload claim displaces the runtime-own one loudly.

== The version chain: four levels, first hit wins.

Every invocation re-evaluates the chain. The environment beats the project, the project beats the config, and the config beats the publisher's default.

*1. Environment — one shell, one pin.*

[source,console]
----
$ export TEBAKO_METANORMA_VERSION=1.2.2
----

The variable name is the tool name uppercased, with non-alphanumerics replaced by underscores — a tool `mn-cli` answers to `TEBAKO_MN_CLI_VERSION`. The environment holds the highest precedence and is the easiest to undo.

*2. Project file — pinned with the code.*

[source,yaml]
----
# .tebako-tools.yaml, at the project root
metanorma: 1.2.1
----

The dispatcher walks up from the current directory; the nearest file that pins the command wins. A nearer file that does not mention the command does _not_ shadow a farther one that does. Commit the file with the project.

*3. Defaults in `~/.tebako/config.yaml`.*

[source,yaml]
----
defaults:
  metanorma: 1.2.3
----

The file is hand-edited. Two commands write it: `tebako add-registry`, and `tebako shim use <tool> <pin>`, which sets a tool's default; there is no top-level `tebako use`.

*4. Registry default — the publisher's word.*

If nothing above pins a version, the registry's own `default:` entry decides.

== Then the runtime.

The chosen entrypoint declares a runtime requirement. The dispatcher picks the newest _compatible_ runtime already in the cache — no download — or, if none fits, downloads, verifies, and caches one. Pure-language payloads declare a range (`>= 3.3, < 5.0`); native-extension payloads pin an application binary interface (ABI) line (`~> 3.3.0`) plus a platform ABI string, and a wrong line is a named error, never a segfault. Entrypoints that need no interpreter — native tools — declare no runtime and get none.

== Preview and diagnose.

[source,console]
----
$ tebako-shim which metanorma
payload     metanorma 1.2.3
version     defaults: in ~/.tebako/config.yaml
image       ~/.tebako/payloads/metanorma/1.2.3.tfs
entrypoint  /bin/metanorma — ruby >= 3.3, < 5.0
runtime     ruby 3.3.7 (cached)
mounts      / (app) · /opt/inkscape · /opt/openjdk
exec        tebako-runtime-… --tebako-image … --tebako-entry metanorma
----

`which` is read-only: it shows what this invocation _would_ dispatch — payload, where the version came from, image, entrypoint, runtime, mounts, and the final exec argv — without running anything. Output above is representative.

[source,console]
----
$ tebako-shim doctor
----

`doctor` checks that the shim directory is on PATH, that every shim resolves, that payload records and their trust anchors exist, that the config parses, that registries are fresh, and that the runtime cache is intact. It ends with _no problems found_ (exit 0) or a problem count (exit 1). The store-wide diagnostic is `tebako doctor`, which carries this same report as its dispatch section; `tebako-shim doctor` remains the dispatcher's own verb.

== Park a version, or a whole tool.

[source,console]
----
$ tebako-shim disable metanorma@1.2.2   # one version
$ tebako-shim disable metanorma          # every version
$ tebako-shim enable metanorma           # bring it back
----

`disable` parks a version — or the whole tool — so dispatch no longer selects it, and `enable` restores it. The state lives in `~/.tebako/shims/.disabled.yaml`: a plain YAML file that can be read or edited.

== Free a PATH name, keep the dispatch.

[source,console]
----
$ tebako-shim hide java       # unlink ~/.tebako/shims/java — the system's java answers again
$ tebako run java -version    # the packaged java still dispatches by name
$ tebako-shim expose java     # relink it
----

`hide` and `disable` are different axes. `disable` keeps the shim on PATH and refuses dispatch, which is the answer to "this version must not run here". `hide` removes the link so the name falls through to whatever PATH resolves next, which is the answer to "my own java lives elsewhere" — and the claim stays dispatchable through `tebako run`. A hidden name stays hidden across reinstalls: install never silently reclaims a name the user freed. The state lives in `~/.tebako/shims/.hidden.yaml`.

== Free the name, keep the tool.

[source,console]
----
$ tebako-shim hide fontist      # the host's own fontist answers again
$ tebako run fontist --help     # the packaged one still dispatches
$ tebako-shim expose fontist    # relink it on PATH
----

`disable` and `hide` answer different questions. `disable` says the payload's command must not run; the shim stays on PATH and refuses by name. `hide` says the command must not shadow: the link leaves `~/.tebako/shims`, so the machine's own tool answers again, while the claim stays dispatchable through `tebako run` and `enable`. The hidden set lives in `~/.tebako/shims/.hidden.yaml`, a plain list in the same shape as the disabled file. A hidden name is never re-linked by a later install; `expose` brings it back. `tebako-shim list` marks hidden commands in text and in the JSON form.

== Per-run overrides at the shim.

[source,console]
----
$ metanorma --jail deny:arg compile site.adoc
$ metanorma --mount "$HOME/extra:/extra:ro" compile site.adoc
----

Leading `--jail`, `--mount`, and `--no-host` tokens are consumed by the dispatcher; everything after them reaches the payload verbatim. The policy grammar is in link:/docs/guides/jails/[the jails guide].
