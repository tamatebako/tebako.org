== The install routes.

All three routes install the same four binaries. Homebrew and the shell installer verify SHA-256 checksums before anything lands; a hand download is verified against the `SHA256SUMS` file on the release.

*Homebrew (macOS, Linux).*

[source,console]
----
brew install tamatebako/tap/tebako
----

The binaries link into the brew prefix, which is already on PATH.

*Shell installer (any Unix).*

[source,console]
----
curl -fsSL https://tebako.org/install.sh | sh
----

The installer detects the platform, downloads the binaries plus `SHA256SUMS`, verifies before installing, and never uses sudo.

*Direct binaries.* The link:https://github.com/tamatebako/tebako/releases[releases page] carries one asset per binary per platform, for `macos-arm64`, `macos-x86_64`, and the ``linux-gnu-* / linux-musl-*`` families:

[source,console]
----
tebako-<ver>-macos-arm64
tebako-pkg-<ver>-macos-arm64
tfs-<ver>-macos-arm64
tebako-bootstrap-<ver>-macos-arm64
tebako-shim-<ver>-macos-arm64
----

The asset names carry the version; the binaries expect the bare names. Rename on download, or `tebako install` stops at the shim step with `the dispatcher binary …/tebako-shim does not exist — shims would point at nothing [74]` after it has already downloaded the payload:

[source,console]
----
$ mkdir -p ~/.local/bin && cd ~/.local/bin
$ for b in tebako tebako-pkg tfs tebako-bootstrap tebako-shim; do
    curl -fsSLO "https://github.com/tamatebako/tebako/releases/download/v<ver>/$b-<ver>-macos-arm64"
    mv "$b-<ver>-macos-arm64" "$b"
  done
$ chmod 0755 tebako tebako-pkg tfs tebako-bootstrap tebako-shim
$ ./tebako --version
Tebako executable packager version <ver>
----

`tebako-shim` is the fifth binary, and the one the hand download is most likely to miss: it is the dispatcher every installed shim links to. It is not needed by `tebako press`, which is why the toolchain is described as four binaries plus the dispatcher.

The installer puts the binaries in `~/.local/bin` (mode 0755) and prints the PATH line for the user's shell. The destination directory is changed with `TEBAKO_INSTALL_DEST`, and a specific release is pinned with `TEBAKO_VERSION`.

== What lands.

The release ships four static binaries: `tebako` (the packager and store CLI), `tebako-pkg` (package trailer surgery and signing), `tfs` (image inspection and creation), and `tebako-bootstrap` (the loader that `tebako press` stitches into every package). Everything they keep on the machine lives under `~/.tebako`.

The dispatcher `tebako-shim` is not among the four. Shims are registered later, by `tebako install`: each shim is a link to a dispatcher binary — by default `tebako-shim` located next to the tebako binary, overridable with `TEBAKO_SHIM_BINARY`.

== Check the install.

[source,console]
----
$ tebako --version
Tebako executable packager version 2.1.7
----

If the shell cannot find `tebako` after the shell installer, the install destination is not on PATH — the installer printed the exact line to add to the shell startup file.

== A first packaged command.

`tebako setup` seeds the official registry, so the managed flow is three commands: a payload is installed from it, the shim directory is put on PATH once, and the tool runs by name.

[source,console]
----
$ tebako setup
fetching registry tfs:github:tebako-packages/registry
seeded the official registry tfs:github:tebako-packages/registry (16 payload(s))
$ tebako install hello
resolving hello
└ toolkit hello 2.12 — fetching
installed payload hello@2.12 (28.3 KB)
shim ~/.tebako/shims/hello
$ tebako-shim install-shell    # once per machine — puts ~/.tebako/shims on PATH
$ hello
Hello, world!
----

The first run of a payload that carries a runtime downloads that runtime once, verifies its SHA-256, and caches it; every later run starts from the cache. Open a new shell after `install-shell` so the PATH change takes effect, or call the shim by path (`~/.tebako/shims/hello`) until you do.

One case does need a registry the guide has not mentioned: installing a **runtime** by name, without an app that carries it.

[source,console]
----
$ tebako install node
Tebako script failed: no registered registry carries a payload named 'node'
  registered registries:
    - tfs:github:tebako-packages/registry
  register one with: tebako add-registry <ref> [65]
$ tebako add-registry tfs:github:tamatebako/tebako-runtime-node
$ tebako install node
installed node 24.22.1 -> ~/.tebako/runtimes/node-24.22.1-2.8.58-macos-arm64
  shim ~/.tebako/shims/node
$ node --version
v24.22.1
----

Each runtime has its own factory repository — `tebako-runtime-node`, `…-bun`,
`…-ruby`, `…-openjdk`, `…-jruby`, `…-truffleruby`, `…-python` under
`tamatebako/` — and the seeded registry does not point at them. A payload that
*depends* on a runtime needs none of this: its manifest names the registry and
`tebako install` fetches it (that is what `` hello-ruby `` does above).

Adding a registry is otherwise only needed for a private or third-party one. Registering a repo that already carries a payload the official registry has makes the bare name ambiguous — the error names both registries and asks for the full reference:

[source,console]
----
$ tebako add-registry tfs:github:tebako-packages/hello-runtimes
$ tebako install hello-ruby
Tebako script failed: payload 'hello-ruby' is listed by 2 registered registries (AmbiguousRegistries):
    - tfs:github:tebako-packages/registry
    - tfs:github:tebako-packages/hello-runtimes
  disambiguate with the full reference: tebako install tfs:<service>:owner/repo:version[#artifact] [65]
----


== Platform notes.

* *musl is the universal Linux artifact.* The ``linux-musl-*`` builds are fully static and run on any distribution. The installer selects them automatically on musl systems such as Alpine.
* *Windows.* The `.exe` assets are downloaded from the releases page. The store lives at `%LOCALAPPDATA%\tebako`.
* *Moving the store.* `TEBAKO_HOME` relocates `~/.tebako`, which is useful for shared caches and continuous integration (CI) sandboxes.

== Uninstall.

Uninstallation deletes the binaries and the store; there is nothing else. The shim PATH block is removed first when `install-shell` was run.

[source,console]
----
tebako-shim uninstall-shell   # if you ran install-shell
brew uninstall tebako           # if you used brew
rm ~/.local/bin/tebako ~/.local/bin/tebako-pkg ~/.local/bin/tfs ~/.local/bin/tebako-bootstrap
                                # ^ if you used install.sh
rm -rf ~/.tebako
----

Runtimes and payloads re-download on demand, but the store also holds the operator's config, signing keys (`keys/`), and pinned publisher keys (`trust/`) — those do not come back.
