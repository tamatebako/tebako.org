== The product repository.

[NOTE]
====
Status: shipped — v0.2.x, five binaries across seven triplets.
====

https://github.com/tamatebako/tebako[tamatebako/tebako] is one Rust
workspace and the whole product: no C/C++, no shell-outs, no system
dependencies in anything it ships. Each release publishes the five binaries
— `tebako`, `tfs`, `tebako-pkg`, `tebako-shim`, `tebako-bootstrap` — for
macOS arm64/x86_64, linux-gnu x86_64/arm64, linux-musl x86_64/arm64, and
windows ucrt64, with SHA256SUMS + manifest.json. Every leg proves its staged
binaries before any upload: a bare launch in the cleanest environment the
leg claims, plus a hard dynamic-dependency whitelist audit
(https://github.com/tamatebako/tebako/blob/main/.github/workflows/release.yml[release.yml]).

Stated plainly: every checksum bundle and manifest ships with a detached
OpenPGP signature (the release trust chain, live since tebako v2.6.0); a
release that is still rolling out platform by platform stays unsigned until
it is complete, and unsigned releases remain first-class. The brew formula
tracks the same five binaries.

=== The crate map.

*The wire*

* https://github.com/tamatebako/tebako/tree/main/crates/tpkg[tpkg] — the
  tpkg trailer + manifest format — parse, serialize, validate. The single
  source of truth for the wire format; `#![forbid(unsafe_code)]`.
* https://github.com/tamatebako/tebako/tree/main/crates/tebako-json[tebako-json]
  — minimal exact-format JSON — writer + small parser, no serde.
* https://github.com/tamatebako/tebako/tree/main/crates/tebako-log[tebako-log]
  — the stack's one debug facility — `TEBAKO_DEBUG` levels, stderr/file
  sinks, component filters.

*The VFS*

* https://github.com/tamatebako/tebako/tree/main/crates/tfs[tfs] — libtfs-rs:
  the `tebako_fs_*` C ABI in Rust (cdylib/staticlib). The shipping TFS
  implementation — the C++ libtfs is its parity oracle.
* https://github.com/tamatebako/tebako/tree/main/crates/sqfs-sys[sqfs-sys] —
  hand-pinned FFI to libsquashfs (squashfs-tools-ng), same discipline as
  dwarfs-t-sys.
* https://github.com/tamatebako/tebako/tree/main/crates/libtfs-preload[libtfs-preload]
  — the preload interposition shim — DYLD_INSERT_LIBRARIES / LD_PRELOAD VFS
  injection for dynamic native binaries.

*The CLI surface (four of the five binaries)*

* https://github.com/tamatebako/tebako/tree/main/crates/tebako-cli[tebako-cli]
  — the `tebako` binary — press / run / install / publish / check / trace /
  cache / info.
* https://github.com/tamatebako/tebako/tree/main/crates/tfs-cli[tfs-cli] —
  the `tfs` binary — the generic VFS image tool: info / ls / tree / cat /
  extract / find / mkimage / exec.
* https://github.com/tamatebako/tebako/tree/main/crates/tebako-pkg[tebako-pkg]
  — tpkg trailer surgery — bundle / unbundle / insert-image / set-runtime /
  sign / verify / validate / info.
* https://github.com/tamatebako/tebako/tree/main/crates/tebako-shim[tebako-shim]
  — the dispatcher + version manager — argv0 resolution, the version chain,
  runtime resolution, the handoff.

*Load time*

* https://github.com/tamatebako/tebako/tree/main/crates/tebako-bootstrap[tebako-bootstrap]
  — the Rust loader — the fifth binary and the process entry point of every
  stitched package. Size-gated, below.
* https://github.com/tamatebako/tebako/tree/main/crates/tebako-driver[tebako-driver]
  — the driver linked inside every runtime exe: mounts the env image +
  payload images, applies the jail, rewrites argv. The Rust successor of the
  v1 C++ tebako-main.

*Shared plumbing*

* https://github.com/tamatebako/tebako/tree/main/crates/tebako-resolve[tebako-resolve]
  — MECE payload references, transport-agnostic fetchers, the shared payload
  cache.
* https://github.com/tamatebako/tebako/tree/main/crates/tebako-http[tebako-http]
  — in-process HTTPS — ureq + rustls, webpki-roots bundled. No curl
  anywhere.
* https://github.com/tamatebako/tebako/tree/main/crates/tebako-signer[tebako-signer]
  — OpenPGP sign/verify via rnp-rs, vendored — no system librnp provisioning.
* https://github.com/tamatebako/tebako/tree/main/crates/tebako-info[tebako-info]
  — the info/inspect surface — payload and package introspection as JSON
  documents.
* https://github.com/tamatebako/tebako/tree/main/crates/tebako-term[tebako-term]
  — terminal progress — TTY detect, hand-rolled ANSI bar/spinner, zero
  dependencies.
* https://github.com/tamatebako/tebako/tree/main/crates/tebako-arscope[tebako-arscope]
  — scopes Rust staticlib symbols for single-link embedding (the
  yjit-collision seal), pure Rust, no shell-outs.

Beside the workspace, not in it:
https://github.com/tamatebako/dwarfs-t-rs[dwarfs-t-rs], the standalone Rust
binding to dwarfs-t — consumed as an ordinary external dependency, tracking
dwarfs-t releases. dwarfs-t itself stays C++ forever; the `dwarfs_c_*` C ABI
is the only Rust-consumable surface.

== The bootstrap size gate.

[NOTE]
====
Status: shipped — hard fail at or above 3 MB.
====

The bootstrap is the process entry point of every stitched package, so its
size is a hard CI gate, not a nice-to-have. Every
https://github.com/tamatebako/tebako/blob/main/.github/workflows/ci.yml[CI run]
builds the release bootstrap per platform, prints it next to the C99 v0.2.0
baseline, and fails at 3,145,728 bytes. The discipline that keeps it there:
`opt-level="z"`, fat LTO, one codegen unit, `panic="abort"`, stripped
symbols; no async runtime, no clap, no logging framework. The budget moved
as the feature set did — and the moves are on record, not swept under:

[cols="2,1,2"]
|===
| ERA | GATE | MEASURED

| C99 bootstrap v0.2.0 — the baseline, six platform binaries | — | 32,512–908,112 B
| Rust bootstrap ships, downloads via curl | < 2 MB | 371,776 B (macOS arm64)
| Downloads go in-process (tebako-http) | < 3 MB — owner-raised when curl was dropped | 1,238,384 B macOS arm64 · 1,664,336 B ubuntu (+867 KB of TLS stack)
| Full static botan ships in the bootstrap | < 6 MB — temporary, owner 2026-07-27 | —
| Today — crypto feature-gated OUT of the shipped bootstrap (unverified-first) | < 3 MB, hard fail | per-platform table on every CI run, printed next to the C99 baseline
|===

The in-process-downloads step and its byte counts are recorded in the
https://github.com/tamatebako/tebako/commit/e3005cdcd524a7c4ab62f8e9d8c2cc863554a976[M7a commit];
the C99 baseline numbers are the published
https://github.com/tamatebako/tebako-bootstrap/releases/tag/v0.2.0[v0.2.0 release assets].

== The golden-parity discipline.

The order is law: if a C++ or gem predecessor exists, golden vectors and
fixtures are generated from it _first_ — no oracle, no parity claim. Then
the ported corpus runs unchanged against the Rust implementation, and parity
legs diff byte-for-byte. That is not a README promise; it is what CI does on
every run:

* CI downloads the C++ oracle binaries — `tebakofs` and `mkdwarfs` from
  https://github.com/tamatebako/libtfs/releases/tag/v0.13.0[libtfs v0.13.0],
  and the
  https://github.com/tamatebako/tebako-bootstrap/releases/tag/v0.2.0[C99 bootstrap v0.2.0] —
  and diffs tebako-pkg / tfs-cli / tebako-bootstrap behavior against them
  byte-for-byte.
* tebako-cli's golden e2e presses side-by-side with the reference gem: same
  fixture, same prefix — the press stdout and the packaged binaries' output
  are diffed.
* The C++ libtfs test corpus, ported to run through the Rust C ABI, lives in
  https://github.com/tamatebako/tebako/tree/main/tests/contract[tests/contract];
  https://github.com/tamatebako/tebako/blob/main/docs/parity.md[docs/parity.md]
  is the audit of what was ported and why.
* An exported-symbol audit passes only when nothing but the `tebako_*`
  surface leaks.
* Anything ported from a C++/gem predecessor is byte-compared, or the
  deviation is documented. A mismatch means the contract moved — and both
  sides must move together.

This is why the two oracle repos are not archived: the parity claim needs
the oracle to exist. libtfs and the C99 bootstrap get no new features — they
stay frozen, citable, and downloaded by the product's own CI.

== What retired: tebako-v1.

The whole v1 implementation — the gem press, the C99 bootstrap as the
shipped product, the C++ driver, the merged env+app image model — is frozen
in https://github.com/tamatebako/tebako-v1[tebako-v1]. It stays readable: it
is the behavioral reference the parity story is proven against, and the
history of why v2 looks the way it does. Nothing new lands there. The
piece-by-piece succession:

[cols="1,1"]
|===
| V1 (RETIRED) | V2 (SHIPPING)

| the tebako gem (press orchestrator) | crates/tebako-cli
| the C99 bootstrap | crates/tebako-bootstrap
| C++ libtfs (shipping VFS) | crates/tfs
| the C++ tebako-main driver | crates/tebako-driver (linked into the runtime)
|===

== The lifecycle rules.

=== Contracts outlive implementations

The `tebako_fs_*` ABI and the tpkg trailer are byte-level contracts.
Consumers don't care which repo ships them — that is what let the Rust
reimplementation ship without a flag day, and it is why the C++ side still
matters as the oracle.

=== Releases are the interface

Repos consume each other's published releases, never source trees. The
factories and the product live in different repos with separate cadences —
the manifest.json contract sits between them, so the packager never
hardcodes a runtime matrix.

=== C++ exactly once

dwarfs-t is the only tebako-owned C++ (upstream ruby's own C is vendored
upstream source, built in the two factories). Everything else is Rust, pure
Ruby tooling, or Docker — no exceptions, no "temporary" ports.

=== dwarfs-t is not legacy

A Rust DwarFS reader/writer is explicitly out of scope. dwarfs-t is
read-only at runtime forever, with the Writer at creation time only; the
only Rust-consumable surface is the C ABI, co-versioned with the C++ it
wraps — which is what dwarfs-t-rs binds.
