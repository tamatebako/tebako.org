== Generic by construction.

One design, generic across four axes. Nothing in the loader, the container, or
the store is Ruby-shaped — Ruby simply happens to be the first runtime the
factories produce.

Any runtime::
A runtime is a payload that _provides_ an interpreter — ruby today; python,
julia, anything later. The loader hands off to an entrypoint; it never learns a
language.

Any platform::
Artifacts are built per platform triplet — seven are locked, from
`aarch64-macos` to `x86_64-windows-ucrt`. Pure-language payloads may also be
`universal`.

Any payload::
Application code, data, fonts, native tools, runtimes themselves — all `.tfs`
images of the same kind, differing only in what their manifests declare.

Any composition::
Payloads stitch onto a single binary, and payloads recursively mount other
payloads at paths. Composition is a manifest declaration, not a rebuild.

== Six capabilities.

Everything tebako does decomposes into six verbs.

[%header,cols="1,3"]
|===
| Capability | What it does

| Stitch
| N payload images + the bootstrap into one executable (fat), or a small executable that resolves the parts on demand (lean).

| Load
| Mount payloads — recursively — into one VFS, then transfer control to the declared entrypoint.

| Share
| Runtimes and payloads download once into a machine-wide content cache; every package on the machine reuses them.

| Shim
| Every executable an installed payload provides becomes a registered command on PATH, dispatched per invocation.

| Jail
| A declarative host-filesystem policy per run, enforced by the VFS layer — not by the payload's good behavior.

| Trust
| Opt-in per package: signatures and encryption. Unsigned stays first-class — verified strictly when signed, never silently downgraded.
|===

Everything orbits one seam: the
link:/docs/architecture/vfs/[tebako_fs_* C ABI], implemented by the Rust tfs
crate. The factories feed it runtimes; feedstock repos — one per package —
build payloads on those runtimes and host them on their own releases
(link:/docs/architecture/factories/[the factories] walk the chain). The trust
layer sits beneath everything that moves bytes.

== The three parts of every package.

A tebako package is a composition of up to three independently distributable
parts, glued by the **tpkg trailer**: a 166-byte header at end of file plus
280-byte slot records. The format version is 1 forever — extensions live in
flags (`LEAN`, `SIGNED_V2`, `NO_INSTALL`), never version bumps, so v1 readers
parse v2 packages untouched. The full byte tables live in
link:/docs/architecture/[concepts].

**A · the bootstrap** — the
link:https://github.com/tamatebako/tebako/tree/main/crates/tebako-bootstrap[Rust loader],
a static binary under 3 MB. It is the process entry point of every stitched
package: reads its own trailer, resolves the runtime, verifies, hands off.

**B · the runtime** — two artifacts, not one: the interpreter executable and
the _env image_ (a `.tfs` carrying the runtime's files). They are downloaded
once into the shared cache, sha256-verified, and
link:/docs/architecture/runtime-as-image/[mounted — never extracted]. Fat
packages carry the runtime as a slot; lean packages carry a reference and fetch
on first run.

**C · the payload slices** — bare `.tfs` images, self-describing via an
in-image manifest (`/__tpkg__/manifest.yaml`). The container's `format_id`
answers exactly one question — how to read the bytes (limnifs, dwarfs-t,
squashfs, zip); whether a slot is a runtime and which payload carries the
entrypoint are manifest semantics, never encoded in the format axis. LimniFS is
the default image format since tebako v0.2.0; dwarfs-t stays first-class as a
read backend.

=== 1 · Standalone — ship the app, hide the machinery.

[NOTE]
====
Status: shipped.
====

A developer presses their app once per platform with the
link:https://github.com/tamatebako/tebako/tree/main/crates/tebako-cli[tebako CLI]
— a single static binary, no host Ruby required — and publishes plain
executables. Their users download one file and run it: no Ruby, no gem
environment, no tebako to install, nothing to know. The _lean_ variant keeps
the download small: the first run fetches the shared runtime once into the
machine-wide cache, where every tebako package on the machine reuses it. The
_fat_ variant carries the runtime inside and never touches the network.

=== 2 · Managed — shims and dispatch.

[NOTE]
====
Status: shipped.
====

A developer publishes **signed .tfs payloads** to their own GitHub releases —
the registry is a `tpkg-registry.yaml` manifest on infrastructure they already
have; there is no central service and no default registry. A user with tebako
installed puts `~/.tebako/shims` on PATH once and just runs `metanorma`: the
dispatcher picks the payload version and a compatible _cached_ runtime — no
download, no per-shell hook. Payloads are immutable; swapping rubies under a
running tool is a dispatch choice, not a reinstall. Native-extension payloads
lock to the ABI line they were built against — honestly, with a named
compatibility error instead of a segfault.
link:https://github.com/metanorma/mnenv[mnenv] retires to the dispatcher —
metanorma is the first dogfood. The mechanism:
link:/docs/architecture/dispatch/[dispatch].

== The engine underneath.

TFS is a product in its own right: a userland virtual filesystem — mount
table, longest-prefix dispatch, pluggable read-only backends, copy-on-write and
encryption transforms above them. The
link:https://github.com/tamatebako/tebako/tree/main/crates/tfs[Rust tfs crate]
**is** the shipping implementation of the `tebako_fs_*` C ABI — 33 exports —
and drives every mount on this page. The C++
link:https://github.com/tamatebako/libtfs[libtfs] survives as the legacy
parity oracle: the Rust ABI runs its contract suite, byte-for-byte.

<img src="/assets/diagrams/tfs-router.svg" alt="The TFS router: calls enter through the tebako_fs_* C ABI; the Rust router dispatches by longest mount-point prefix onto read-only backends — limnifs, dwarfs-t, squashfs, zip, tar — with a copy-on-write overlay above; paths outside every mount pass through to the host filesystem" class="w-full min-w-[760px]" loading="lazy" />
</figure>
++++

_Figure 6 — The TFS router: longest-prefix dispatch onto read-only backends, with a copy-on-write overlay above and pass-through to the host outside every mount._

Any project, in any language, can attach images to its binaries through the
same ABI, or drive images from the shell with the
link:https://github.com/tamatebako/tebako/tree/main/crates/tfs-cli[tfs CLI].
link:https://github.com/tamatebako/dwarfs-t[dwarfs-t] — the only C++ in the
ecosystem — and
link:https://github.com/tamatebako/dwarfs-t-rs[dwarfs-t-rs], its standalone
Rust binding, are consumable without knowing tebako exists. Every backend is
read-only at runtime forever; writing exists only as the copy-on-write overlay
plus a creation-time Writer. The full model:
link:/docs/architecture/vfs/[the VFS model].

== The trust chain.

One signature mechanism — OpenPGP via rnp-rs — from the publisher's key to the
user's run. Signing is per-package opt-in; verification of anything signed is
always strict. Verification happens at install, never per run; failures are
named exits, never crashes. Details:
link:/docs/architecture/chain-of-trust/[the chain of trust].

_Figure 7 — The tebako chain of trust: root key, release keys, per-artifact SHA256 digests, and the tpkg v2 signature verified at install._

[NOTE]
====
*Stated plainly: the rollout phase.* Today's shipped loader is built
**without** OpenPGP verification — the unverified-first rollout. Signed
packages run with a loud `UNVERIFIED` warning plus an audit-journal entry
while their per-slot sha256 is still enforced as integrity; unsigned packages
run with the legacy warning. `TEBAKO_REQUIRE_SIGNED=1` fails closed with exit
71 — a strict-mode request is never silently downgraded. Full signature
verification in the loader returns with the crypto-toolkit payload. The
target model — embedded root fingerprint, TOFU key pins under
`$TEBAKO_HOME/trust/`, exits `70` (sha256 mismatch), `71` (bad signature),
`72` (untrusted or changed signer key) — is on
link:/docs/architecture/chain-of-trust/[the chain-of-trust page].

== Who it's for.

The audience rule, stated once: prebuilt artifacts flow downward; compilation
never flows outward. Only people building tebako itself ever compile tebako.

People running packages::
No compilation machinery, no libraries, nothing to install — download it and
run it. With a fat package, not even a network. With tebako installed, one
shims directory on PATH puts every managed tool a command away, with version
pinning that just works.

Developers shipping data::
Data-only payloads need no compilation machinery: `tfs mkimage`, a manifest,
a release. Fonts, datasets, tool assets — content-addressed, signed if you
want it, mounted whole.

Developers shipping applications::
You compile only your own code. Tebako itself arrives as binaries; the
runtimes are prebuilt downloads. Press once per platform in a matrix CI job —
no heroics per target — and publish to releases you already own.

People hacking on tebako::
The only audience that needs the tebako toolchain: the factories, the product
workspace, the contract suites. Start with
link:/docs/architecture/repositories/[the repo map] and
link:/docs/architecture/contributors/[the contributor page].
