[NOTE]
====
The CLI on the 0.2.x line and the ruby runtimes on the 0.16.x line ship
today, and the migration path below is live.
====

== The short version

*If you run tebako packages:* uninstall the gem-era tooling, install the v2
CLI, and keep working. Packages pressed with v1 must be re-pressed, because
v1 embedded images do not load in v2.

*If you press packages:* your workflow no longer needs CMake, compilers, or
system libraries on the packager's machine. The packaging tools arrive as
binaries.

*If you pinned a Ruby version:* the pin becomes a runtime constraint in the
payload manifest (`runtime_requirement: ruby "~> 3.3.0"`). Runtimes download
once and are shared by every package on the machine.

== What changed, in one table

[cols="1,2,2"]
|===
| Area | v1 (archived) | v2 (current)

| Implementation | C++ (tebako-main, libtfs) + the tebako gem | Rust end to end (bootstrap, shim, driver, tfs, tpkg, CLI)
| Runtime | one merged environment+app image, embedded | interpreter exe + separate env image; shared, downloaded once
| Payloads | opaque embedded images | self-describing slices (`/__tpkg__/manifest.yaml`), co-mounted
| Packaging tools | compiled on your machine (CMake + system libs) | prebuilt binaries per platform
| Distribution | one fat binary only | fat/lean binaries _and_ the managed store (registries, shims, version manager)
| Native tools | not supported | zero-runtime payloads (Inkscape, JRE, hello) as first-class slices
|===

== The command map

[cols="2,2,3"]
|===
| v1 (gem) | v2 | Notes

| `gem install tebako` | `brew install tamatebako/tap/tebako` | prebuilt per platform; no compilers
| `tebako press …` (the gem) | `tebako press …` (the Rust CLI) | same verb, prebuilt binary; lean/fat — classic mode is gone
| — (no install verb) | `tebako add-registry … && tebako install …` | the managed flow: registries, store, shims
| `RUBY VERSION` pin | `runtime_requirement: ruby "~> 3.3.0"` | in the payload manifest; the dispatcher resolves it
|===

== The flags you remember

A request for help with a v1 command usually names one of four flags, and each of them has a current spelling. The two that changed name are the two that most often appear in older tutorials.

[cols="2,3,3"]
|===
| v1 flag | v2 flag | What changed

| `--tebako-mount <host>:<mount>` | `--image <path>:<mount>` on `tebako press`, repeated once per slice | A mount is now a payload slice with its own image, and the option names the image rather than a host directory. Naming a host directory is the jail's `--mount`, a different mechanism with the same word.
| `--cwd <dir>` | `-c <dir>` on `tebako press` | The package working directory is baked at press time; the default remains the host's current directory at run time, which the press announces.
| `-m lean` / `-m fat` | `-m shared-runtime` / `-m self-contained` | The two names say what the package does rather than how large it is. `lean` and `fat` stay accepted as deprecated aliases.
| `tebako setup` (compile the toolchain) | `tebako setup` (seed the official registry) | The verb survives with a different meaning. Nothing is compiled: a runtime arrives as two published artifacts, and `setup` writes the default registry into the configuration so that `tebako install` has an index to search.

|===

The remaining press flags kept their v1 spelling: `-r` for the project root, `-e` for the entry, `-o` for the output, `-p` for the prefix, `-R` for the runtime line, and `--sign` for signing at press time. The full surface is printed by `tebako press --help`, and link:/docs/guides/package-ruby/[Package a Ruby app] describes each option in the order it is used.

== The steps, in order

. *Remove the gem-era install.* `gem uninstall tebako` and drop any v1
  build trees. The v1 repo is archived at
  https://github.com/tamatebako/tebako-v1[tamatebako/tebako-v1], a read-only
  reference with no new development.
. *Install the v2 CLI.* `brew install tamatebako/tap/tebako` (or the
  per-platform release asset from
  https://github.com/tamatebako/tebako/releases[tamatebako/tebako]).
. *Re-press your payloads.* v1 images do not load in v2. For a Ruby app:
  declare the runtime constraint in the manifest, press with `tebako press`
  (lean or fat), and either ship the stitched executable or publish the
  payload to a registry for the managed flow. Data and toolkit slices are
  built with `tfs mkimage`.
. *First run downloads the runtime once.* It lands in
  `~/.tebako/runtimes/`, SHA-256 verified, shared by every tebako package
  on the machine. Subsequent runs are silent cache hits;
  `TEBAKO_OFFLINE=1` makes that explicit.

== Points worth knowing

* *The env image is not your app.* v1 merged them; v2 never does. The
  runtime's env image is the interpreter's stdlib and gems, and your app is
  a separate payload slice mounted over it.
* *Native tools are slices now.* If your app shells out to a binary
  (Inkscape, a JRE, ffmpeg), package it as a toolkit payload and declare it
  in `requires:` with a mount point. Your users stop installing it by hand.
* *A run never installs.* Executing a package reads and runs only; `tebako
  install` is the explicit verb that populates the store and registers
  shims.
* *Unsigned is first-class, loud.* Unsigned payloads install with a warning
  and a journal line; `TEBAKO_REQUIRE_SIGNED=1` fails closed. Signing is
  opt-in per package.
