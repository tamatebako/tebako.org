== Build: press.

[source,text]
----
tebako press -r <root> -e <entry> [-o <output>] [-p <prefix>] [-c <cwd>]
             [-R <ruby>] [-m self-contained|shared-runtime] [-l error|warn|debug|trace]
             [--image <path>:<mount>]... [--bootstrap <path>]
             [--tebako-version <v>] [--prefer-local] [--jail <spec>]
             [--no-install] [--quiet-notices] [--sign[=<keyid>] | --no-sign]
             [--format dwarfs|limnifs] [--exclude <glob>]... [--compose <tebako.yaml>]
             [--carry all|none|<name,...>] [--share <name,...>]
             [--emit-recipe[=<path>]]
----

The `lean` and `fat` mode names stay accepted as deprecated aliases of `shared-runtime` and `self-contained`. A suite presses one package with N commands:

[source,text]
----
tebako press --suite <suite.yaml> [-o <output>] [-p <prefix>] [-R <ruby>]
----

`--emit-recipe` renders the feedstock recipe for the press that just succeeded, which is the graduation path from a directory press to a feedstock repository. The rendered document names the engine, the entry point, the mode, the image format, the vendored lockfile, the resolved runtime pair together with the factory release the pair came from, the platform leg the press proved and the executable the payload provides. The bare flag writes `Tebakofile` at the project root; a value writes the document to that path. A file the command did not generate is never overwritten, because an authored recipe is the author's property.

Signing at press resolves through the settings registry — the CLI flag wins, then the environment, then the compose document. Only the CLI may name a key. The task-oriented walkthrough is the link:/docs/guides/package-ruby/[Package a Ruby app] guide.

== Run: run.

[source,text]
----
tebako run <pkg> [--jail <spec>] [--mount <host:mount:ro|rw>]... [--no-host]
            [--] [<args>...]
tebako run <engine>[:<command>] [<args>...]
----

Everything after `--` reaches the payload verbatim; the flags before it shape this run only. When the first token names no existing file it is read as an engine reference and boots that runtime directly — the bare form runs the interpreter, the colon form a command the runtime declares. The guide is link:/docs/guides/run/[Run a packaged app].

== Trace: run, cover, import, explain.

The trace verbs form the interception-bus toolkit; the task-oriented walkthrough is the link:/docs/guides/trace/[Trace a packaged app] guide.

`tebako trace run` runs a package under the record policy with the trace bus armed and synthesizes a suggested manifest — commented YAML on stdout, never applied:

[source,text]
----
tebako trace run <pkg> [--capture <path>] [--out <path>] [--] [<args>...]
----

`tebako trace cover` subtracts the inside stream from an outside capture and reports the escapes (exit 0 clean, 1 escapes, 2 error):

[source,text]
----
tebako trace cover --inside <tfs.json> --outside <retrace.json> --prefix <path>
                   [--pid N] [--window SECS] [--exclude-probes] [--json] [--layer libc|kernel]
----

`tebako trace import procmon` converts a procmon CSV export into the retrace-shaped JSON that cover consumes (exit 0 converted, 1 zero entries, 2 error):

[source,text]
----
tebako trace import procmon <capture.csv>
----

`tebako trace explain` replays a capture into the hop chain and names the first red hop (exit 0 clean, 1 red hop, 2 error):

[source,text]
----
tebako trace explain <capture.jsonl>
----

== Check.

The verb runs the payload's in-image acceptance checks against a name, an image, a package, or a compose document:

[source,text]
----
tebako check <name | image.tfs | package | tebako.yaml>
             [--check <c>] [--list] [--record] [--keep-scratch]
             [--runtime <exe> --runtime-image <env.tfs>]
----

The guide is link:/docs/guides/check/[Check a payload].

== The store: cache, install, uninstall, info, inspect.

[source,text]
----
tebako cache list [--json]
tebako cache prune [--all] [--older-than Nd]
tebako install <ref | name[@ver]>
tebako install <engine>[:<command>]
tebako uninstall <name>
tebako info [topic] [--remote] [--json]
tebako inspect <artifact> [flags]
----

`tebako install` installs a payload and registers its shims, and the engine form pre-stages that engine's runtime and registers a runtime-own shim instead (the bare form registers the interpreter's own name, the colon form the declared command's name). `tebako uninstall` removes the shims and the cache entry. `tebako info` reports on the store and its contents — the topics are system, runtimes, payloads, shims, registries, and store. `tebako inspect` reads a single artifact; `--contract` prints the contract card: the era, the contract versions, mount_root, the ABI, and the trust verdict. The guide is link:/docs/guides/info-inspect/[info & inspect].

== Trust material: keys, trust.

[source,text]
----
tebako keys import <file>
tebako keys list
tebako keys remove <fingerprint>
tebako trust add <file.pem>
tebako trust list
tebako trust remove <name>
----

The two families cover the two keyrings a run consults, and neither of them is the host's.

The signing keyring answers the question of who may have made an artifact. `tebako keys import` registers a public key into it, `tebako keys list` reports the trusted signing keys together with the root, the keyring and the pins, and `tebako keys remove` drops a key from both the keyring and the pin store, so a removed key cannot keep vouching for a pinned digest through the store alone.

The TLS trust store answers the question of which certificate authorities a fetch may trust, and `tebako trust add`, `tebako trust list` and `tebako trust remove` are its whole surface. The store exists because a corporate proxy that inspects TLS presents a certificate the host trusts and a packaged runtime cannot see: the driver exports this store to the interpreter through `SSL_CERT_FILE` at mount time. The guide is link:/docs/guides/verify/[Verify integrity], and the enterprise walkthrough is link:/docs/guides/enterprise-networks/[Enterprise networks].

== Setup and the dispatcher: setup, shim.

[source,text]
----
tebako setup
tebako shim <verb> ...
----

`tebako setup` seeds the official registry into the machine's configuration. It is the step an installer runs on a fresh machine, it is idempotent, and the row it writes is an ordinary configuration row the user may remove, which is why a machine that has run it carries no privileged state.

`tebako shim` is the dispatcher behind every registered command, and it is the same program as `tebako-shim`, so the verbs are `list`, `use`, `enable`, `disable`, `which`, `doctor`, `install-shell` and `uninstall-shell`. The verb reference is link:/docs/reference/cli-tebako-shim/[tebako-shim CLI], and the version chain a shim resolves per invocation is in link:/docs/guides/shims/[Shims & versions].

== Registries: add, list, update, validate, retire, doctor.

[source,text]
----
tebako add-registry <ref>
tebako list-registries
tebako update-registries
tebako registry validate <path-or-url> [--json]
tebako registry retire <registry-file> <name>@<version> [--force]
tebako registry doctor <path-or-url> [--full] [--sample <n>] [--json]
----

`tebako add-registry` registers a tpkg-registry.yaml; `tebako update-registries` refreshes the dispatch-time registry cache. The guides are link:/docs/guides/publish/[Publish to your own registry] and link:/docs/guides/library/[Curate a local library].

`tebako registry validate` runs the reader every install and dispatch path runs, together with the stricter checks a pipeline gate wants collected in one report, and the exit code is the verdict: zero for a valid document and 65 for an invalid one. `tebako registry retire` removes one version row from a local registry file, refusing while the removal would strand a runtime edge, dangle the payload's default, or delete the payload's last row; `--force` overrides each refusal loudly.

`tebako registry doctor` extends the document gate to the host that serves it. The reference is parsed into its transport class, the document is validated, and every row is resolved for the host platform through the same resolver an install runs. An artifact the host does not serve, a digest that disagrees with the row's pin, and a signature that does not verify are problems; a platform the payload is not published for is a note, because the platform matrix belongs to each payload. `--full` downloads the resolved artifacts, which makes the digest and signature checks real; it samples one version per payload unless `--sample` names a larger count. The exit code is zero for a conformant registry and one when problems were found, and `--json` emits a `registry_doctor_schema` document for pipelines.

== Publish.

[source,text]
----
tebako publish --name <app> [--version <v>] --release tfs:github:<owner>/<repo>[:<tag>]
               (--payload <path> | --payload <triplet>=<path>)...
               [--standalone <triplet>=<path>]... [--sign[=<keyid>]]
               [--upload-mirror <dir>] [--tap <org/homebrew-tap> [--tap-dir <dir>]]
               [--registry-out <path>] [--skip-verify]
----

The publisher's GitHub releases are the storage; the command writes the index consumers add. The walkthrough is the link:/docs/guides/publish/[publish guide].

== Bundle.

[source,text]
----
tebako bundle <name[@ver]> --output <dir> [--config <org.yaml>] [--archive tar.gz]
----

The verb assembles an offline bundle: the payload's whole dependency closure plus the runtimes it needs, gathered into one directory (optionally archived) that installs and runs with no network. Bundling draws from the local store and refuses a partial set by name — the closure is cached first.

== Diagnose: doctor, audit.

[source,text]
----
tebako doctor [--json]
tebako audit [--since <t>] [--until <t>] [--event <e,...>] [--artifact <needle>]
            [--tail <n>] [--count] [--json] [--strict] [--seal] [--verify]
----

`tebako doctor` is the read-only diagnostics surface: five sections (store, dispatch, network, trust, registries) carry a named verdict on every check, with exit 0 when healthy and 1 with a problem count. `--json` prints the same report as a machine-readable document. The dispatch section is the `tebako-shim doctor` report rendered in place.

`tebako audit` reads the ledger, which records what this host fetched, verified, mounted and ran. The query flags select by time window, by event name and by an artifact substring, `--tail` bounds the output and `--count` answers with counts instead of rows. The command is read-only until `--seal` anchors the ledger's current head, after which `--verify` recomputes the chain and compares it to that anchor: exit zero means the anchor holds and exit 80 means a finding, with exit 74 for a ledger that carries no anchor and 64 for a usage error. A damaged line is always reported with its line number and raw bytes, and `--strict` promotes that report to exit 80. The guide is link:/docs/guides/verify/[Verify integrity].
