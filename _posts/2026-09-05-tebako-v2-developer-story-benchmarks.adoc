= Build your own: feedstocks, presses, and the benchmark table

The first four posts described what users get. This one is for the
people who *build* packages — the pipeline behind "one download," and
the numbers that keep it honest.

== The pipeline: feedstock → release → registry → press → shim

// source: ecosystem charter §5/§9 (the feedstock model and the release
// chain); docs/spec/13 (factories and releases); spec 04 (registries).
Every tebako package comes out of the same five-stage pipeline:

. **The feedstock** — one repository per package in the
  `tebako-packages` org (the conda-forge model): a recipe, patches,
  manifest templates, and CI. The feedstock builds its payload per
  platform triplet — or once as `universal` when the bytes are
  pure-language.
. **The release** — the feedstock's releases host the payload artifacts
  plus their SHA-256 sidecars. Repos consume each other's *published
  artifacts*, never source trees.
. **The registry** — a YAML index the same repo hosts and regenerates
  per tag; it mirrors resolution fields only. Users point at it with
  `tebako add-registry`; there is no central service.
. **The press** — `tebako press` resolves the full composition closure
  at build time — runtime plus every payload, transitively — and locks
  concrete versions and digests into the package manifest. *What press
  tested is what runs*: a shared slice resolves at run time by locked
  digest, never by fresh semver.
. **The shim** — `tebako install` registers the payload's declared
  commands on `PATH`, with per-invocation version dispatch through the
  documented chain (environment → nearest `.tebako-tools.yaml` →
  store config defaults → registry default).

// source: PROGRESS/00-INDEX.md (the packed-mn re-pin entries:
// one-file version/digest bumps, script-verified against the releases'
// SHA256SUMS); spec 00 invariant 10 (SSOT for every cross-repo value).
The single-source-of-truth discipline is the part worth stealing.
packed-mn — the single-executable Metanorma distribution — keeps every
moving pin in *one file*, `versions.yaml`: the tebako toolchain
release, the runtime line with its per-triplet digests, the payload
versions with theirs. A bump is a one-line edit plus digest refresh,
script-verified against the upstream release's published sums; nothing
else in the pipeline hardcodes a version. When a value exists in two
places, one of them is generated — that is the ecosystem's SSOT
invariant, and it is why the release chain can re-cut a runtime line
and have every downstream consumer notice exactly once.

== One pipeline, many runtimes

// source: docs/spec/28 (the engine/implementation spelling); spec 30
// (the kind: runtime edge; first instance = the java engine);
// spec 29 (the wrapper pattern for repacked runtimes);
// PROGRESS/00-INDEX.md 2026-09-01 (python/01 skeleton; TODO.jruby/01
// is runtime-on-runtime composition).
The runtime axis is generic, and it is no longer a one-engine claim:

* **ruby** (MRI) — the reference engine: patched-source factory,
  interpreter exe plus env image, the driver linked in at factory time.
* **java** (Temurin) — landed with v2.1.0: the first *repacked*
  runtime, shipped through the wrapper-exe pattern (spec 29) and
  consumed through the spawned-dependency edge (spec 30) that post 3
  walked through.
* **python** — the factory skeleton exists; the relocation probe
  already returned *relocatable, zero patches* for CPython 3.12/3.13.
* **jruby / truffleruby** — queued; those are *runtime-on-runtime*
  composition (a runtime whose process owner is another runtime), a
  different mechanism from the spawned edge, with its own design queue.

A payload declares its engine, implementation, and constraint in the
same manifest grammar regardless of engine; resolution, locking, and
the store layout do not change.

== Prove it: payload checks

// source: docs/spec/26 (the payload-check framework); spec 23 §13.3
// (the honesty proof: a universal claim with native bytes fails in CI
// before publication); tebako-packages/metanorma (the compile-a-
// document acceptance).
"Works on my machine" is not a release criterion. The payload-check
framework (spec 26) gives every feedstock a declared, in-image
acceptance check that CI runs on *every* target triplet before
publication. Metanorma's check is the model: compile a real document —
the acceptance suites drive xml, html, rxl, and PDF legs, fonts and
spawned java included. The check is also the honesty proof for
`universal` claims: an image declared platform-independent that smuggles
native bytes fails there, before a user ever downloads it.

== The benchmark table

// source: docs/spec/27 (the benchmark contract); PROGRESS/13 (the
// bench suite: tebako-bench + benchmarks/{suite,platforms}.yaml,
// YAML-SSOT, the report renderer re-deriving stats, speedups vs the
// v1-* baseline cells, cold runs reported separately).
Benchmarks in this ecosystem are infrastructure, not blog garnish: the
suite is declared in versioned YAML (one file for the workloads, one
for the platform matrix — the workflow's matrix is *generated* from
them), the harness drives released, checksum-verified artifacts only,
and the report renderer re-derives every statistic from the raw
measurements rather than trusting carried numbers. The comparison that
matters for this series: the v2 line — current tebako and runtime —
against the v1-era packed-mn executables it replaces, cold runs
reported separately from warm.

The refresh ran on 2026-09-04 — the publish-time measurement of this
series' comparison, the managed arm riding payload 1.16.9-8 + ruby
runtime 0.16.21 + tebako v2.1.7: the release line that closes the
jing/spawned-java arc named in post 3. The pdf column *is* the fix's
proof — every managed-arm compile runs RELAX NG validation and mn2pdf
through the spawned tebako java runtime, end to end, exit 0.

[cols="<4,>3,>3,>2", options="header"]
|===
| warm workload (n=5, median wall) | packed-mn v1.16.9 exe | tebako v2 managed + shim | v2 vs v1

| `compile document.adoc -x html` | 51.9 s | 52.5 s | 1.01×
| `compile document.adoc -x pdf` | 61.0 s | 67.1 s | 1.10×
| `metanorma version` boot | 4.70 s | 4.06 s | 0.86×
|===

Peak RSS moves the right way on every row: html 1.38 → 1.22 GiB, pdf
1.35 → 1.29 GiB, boot 0.99 → 0.76 GiB.

[cols="<4,>3,>3", options="header"]
|===
| cold (fresh store, single run) | packed-mn v1.16.9 exe | tebako v2 managed

| html compile | 119.1 s | 88.0 s
| pdf compile | 145.4 s | 98.0 s
| first `metanorma version` | (runtime baked at install) | 57.2 s
|===

The footer the suite contract demands. Machine: MacBookPro18,2, Apple
M1 Max, 64 GB, macOS 14.1.1, measured idle. Document: mn-samples-oiml's
OIML r060 (`ba74c74`), html and pdf compiles; outputs verified
regenerated in every cell (byte-identical html across arms; %PDF-1.7).
The v1 arm carries metanorma 2.5.2, the v2 arm 2.5.4 — the payload line
moved between the packagings, so the compile columns compare
*packagings*, not metanorma releases. Cold cells are single indicative
runs with the runtime download in span; the managed arm's install
pre-stages payload images per spec 27 §5. And the noise note: a Sep 1
dry run of this same suite on a busy desktop read ~2.3× slower on
*both* arms — within a day the ratios are the comparison; across days
the absolutes are indicative.

The read: compile parity on html (1.01×), within 1.10× on pdf, and a
smaller, faster boot (0.86×, 0.76 GiB against 0.99 GiB) — the managed
composition costs nothing measurable against the one-file exe it
replaces, and the cold start is faster even with the runtime download
in the span.

== Where this leaves you

A user downloads a file and runs it. A payload author writes a recipe
and a manifest, and never asks a user for a compiler. A runtime
operator adds an engine without touching the loader. And every layer
says what it does in a document you can read before you run it —
manifest, composition, jail, lock.
