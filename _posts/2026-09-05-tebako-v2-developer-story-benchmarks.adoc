== Step 1: press a data payload

The simplest package there is: a directory of files and a manifest.

[source,console]
----
$ mkdir -p acme-fonts/__tpkg__ fonts
$ mv ~/Downloads/acme-*.ttf fonts/
$ cat > acme-fonts/__tpkg__/manifest.yaml <<EOF
schema_version: 1
kind: data
name: acme-fonts
version: 2.1.0
provides:
  paths:
    - /fonts
EOF
$ tfs mkimage acme-fonts/ -o acme-fonts-2.1.0.tfs
----

No code, no compilation — one command, one image. Anyone can mount it,
and chapter 3 already showed you how.

== Step 2: package an application

Give `tebako press` a source tree, an entrypoint, and a name:

[source,console]
----
$ tebako press -r ./myapp -e bin/myapp -o myapp
----

That is a complete package: press resolves your dependencies, presses
the slices, and stitches the trailer. Add the fonts slice and the jail
from chapter 4 in the same command:

[source,console]
----
$ tebako press -r ./myapp -e bin/myapp -o myapp \
    --image acme-fonts-2.1.0.tfs:/usr/share/fonts/acme \
    --jail ./jail.yaml
----

== Step 3: prove it works

A payload can carry its own acceptance test, declared in its manifest
and run with one command:

[source,yaml]
----
checks:
  html-xml:
    entry: /bin/metanorma
    argv: ["--type", "iso", "{scratch}/test-iso.adoc", "--agree-to-terms"]
    fixtures: /__tpkg__/check/html-xml
    expect: { exit: 0, files: ["test-iso.xml", "test-iso.html"] }
    timeout: 180
----

[source,console]
----
$ tebako check ./myapp
slice myapp: html-xml PASS 41s
----

A missing prerequisite *skips* with a reason and never fails; a real
failure exits 79 and names the expectation that failed. Run the checks
in CI and a broken payload cannot reach your users.

== Step 4: publish it

Publishing puts a registry — one YAML file — on your own release:

[source,console]
----
$ tebako publish --name acme-tool --version 1.4.0 \
    --release tfs:github:acme/acme-tool:v1.4.0 \
    --payload macos-arm64=dist/acme-tool-1.4.0-macos-arm64.tfs \
    --payload linux-gnu-x86_64=dist/acme-tool-1.4.0-linux-gnu-x86_64.tfs
published acme-tool 1.4.0 -> tfs:github:acme/acme-tool (tag v1.4.0)
sha256 9f2c…a1  acme-tool-1.4.0-macos-arm64.tfs
sha256 77b1…0e  acme-tool-1.4.0-linux-gnu-x86_64.tfs
----

Your users install from it with two commands:

[source,console]
----
$ tebako add-registry tfs:github:acme/acme-tool
$ tebako install acme-tool
----

No server to run, no store to submit to: your releases are the
registry, and every artifact carries its SHA-256.

== The numbers

The v2 composition your users get is measured against the one-file
executable it replaces, on the metanorma workload from chapter 1:

[cols="<4,>3,>3,>2", options="header"]
|===
| warm workload (n=5, median wall) | packed-mn v1.16.9 exe | tebako v2 managed + shim | v2 vs v1

| `compile document.adoc -x html` | 51.9 s | 52.5 s | 1.01×
| `compile document.adoc -x pdf` | 61.0 s | 67.1 s | 1.10×
| `metanorma version` boot | 4.70 s | 4.06 s | 0.86×
|===

Peak RSS moves the right way on every row: html 1.38 → 1.22 GiB, pdf
1.35 → 1.29 GiB, boot 0.99 → 0.76 GiB.

[cols="<4,>3,>3", options="header"]
|===
| cold (fresh store, single run) | packed-mn v1.16.9 exe | tebako v2 managed

| html compile | 119.1 s | 88.0 s
| pdf compile | 145.4 s | 98.0 s
| first `metanorma version` | (runtime baked at install) | 57.2 s
|===

Machine: MacBookPro18,2, Apple M1 Max, 64 GB, macOS 14.1.1, measured
idle; document: mn-samples-oiml's OIML r060 (`ba74c74`), outputs
verified regenerated in every cell. Compile parity on html (1.01×),
within 1.10× on pdf, a smaller and faster boot — the managed
composition costs nothing measurable against the one-file executable,
and the cold start is faster even with the runtime download included.
