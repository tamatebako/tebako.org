Metanorma, the standards-authoring toolchain we build, is the hardest
packaging workload we know: a Ruby application that drives a Java
XSL-FO converter, calls Inkscape to rasterize figures, and uses a
Python tool for the IETF document flavors. This post shows that whole
stack running as one tebako v2 package on a machine with nothing
installed, and then opens the package to show exactly what is inside
and how each part gets there.

This is the first post in a five-part series. Post 2 opens the package
format in depth; this one gives you the working model first.

== The 90-second demo

// PROGRESS/13-benchmarks.md (2026-08-30 D0 acceptance run: the packed-mn
// darwin-arm64 asset compiled mn-samples-oiml r060 to all four outputs,
// COMPILE_EXIT=0).
Here is the entire setup on a machine that has none of Ruby, Java, or
Inkscape installed:

[source,console]
----
# install tebako itself (prebuilt, per platform)
brew install tamatebako/tap/tebako

# point at the metanorma payload registry and install
tebako add-registry tfs:github:tebako-packages/metanorma
tebako install metanorma

# it's on PATH now — the ruby runtime downloads on first run
metanorma compile document.adoc
----

You can also skip the store entirely: the
https://github.com/metanorma/packed-mn[packed-mn project] ships
Metanorma as a single executable per platform. You download one file
and run it; the runtime it needs is downloaded and verified the first
time you use it, and it is then shared by every tebako package on the
machine.

The following command on an OIML Recommendation written in Metanorma
outputs all four kinds of format:

[source,console]
----
$ metanorma compile sources/r060/1/document.adoc
# → document.xml  (191 KB)   the semantic XML
# → document.html (225 KB)   the HTML rendering
# → document.rxl  (11 KB)    the Relaton bibliographic extract
# → document.pdf  (751 KB)   the print-ready PDF
----

// source: PROGRESS/13-benchmarks.md 2026-08-30 — byte counts from the
// D0 local acceptance run against the published packed-mn asset.
The PDF step matters most, because it is where the borrowed machinery
shows: the converter runs a Java XSL-FO engine (mn2pdf) and a Java
validator (jing), rasterizes the figure with Inkscape, and embeds the
fonts it resolved at compile time. Every one of those technologies
arrived with the package — none of them was installed on the machine.

== How tebako works

Tebako packages an application so it runs anywhere, without installing
anything else. A package has three kinds of parts:

. *The bootstrap* — a small Rust loader (under 3 MB). It is the
  executable's entry point: it reads the package trailer, finds the
  runtime, and hands control over.
. *The runtime* — the language interpreter your application needs,
  shipped as two files: the interpreter executable and an environment
  image (the standard library and gems, as a mounted disk image). The
  runtime is downloaded once per machine into `~/.tebako`, verified
  against its published SHA-256, and shared by every package.
. *Payload slices* — your application, your data, and the tools it
  needs, each a disk image that describes itself with a manifest.

When you run a package, this is the whole sequence:

. The bootstrap reads the trailer at the end of its own file. The
  trailer names the runtime and lists the slices stitched into the
  executable.
. If the runtime is not in the store yet, the bootstrap downloads it,
  verifies it against the published digest, and caches it.
. A component inside the runtime called the driver mounts the
  environment image at the interpreter's root, then mounts each payload
  slice at the path its manifest declares.
. The interpreter starts on your application's entrypoint. The files
  your program reads are served from the mounted images, in memory —
  nothing is extracted to disk.

Post 2 walks this anatomy with diagrams; the rest of this post applies
it to a package you can download today.

== How packed-mn maps to the parts

The packed-mn executable is one tebako package. Here is every piece
of it, which tebako part it is, and where it lives when you run it:

[cols="2,3,3",options="header"]
|===
|What you meet |Which tebako part it is |Where it lives

|The executable you download
|The bootstrap, the stitched payload slots, and the trailer
|One file — that is the whole download

|Metanorma 1.16.9, with its 260 gems
|Payload slice 1.16.9-8
|Stitched into a slot inside the executable

|Ruby 3.3
|The runtime 0.16.21, named in the trailer
|Downloaded once to `~/.tebako`, verified, shared by every package

|OpenJDK 21 (Temurin 21.0.12), for mn2pdf and jing
|Spawned runtime 2.1.5
|Resolved from the registry into the store on first use

|Inkscape, for figure rasterization
|A mounted payload slice, declared as a dependency
|Mounted at `/opt/inkscape` at run time

|xml2rfc, for the IETF flavors
|A declared *host tool* — used only if your machine provides it
|Your machine, stated openly in the manifest
|===

Three different routes bring the non-Ruby machinery in, and each is
deliberate:

* *Java* is a spawned runtime. When Metanorma's Ruby code runs `java`,
  tebako starts the OpenJDK runtime's own executable with its own
  environment image — the JVM never sits inside the Ruby process and
  never comes from a host `PATH`.
* *Inkscape* is a mounted payload. The Metanorma slice declares that it
  needs the Inkscape slice at `/opt/inkscape`, and the driver mounts it
  there — payload depending on payload is an ordinary declaration.
* *Python* is the one honest host-tool route: a system tool, used when
  the host has it, and declared as such so nothing is hidden.

None of this needs Homebrew, `apt`, or a `JAVA_HOME`: a user who has
never heard of Java or Inkscape gets exactly the same document.

== Migrating from v1

The C++/CMake era is archived as
https://github.com/tamatebako/tebako-v1[tebako-v1] and receives no new
development. v1 embedded images do not load in v2; press fresh payloads
with the v2 tooling. The migration notes in our
link:/blog/2026-07-31-tebako-v2-hermetic/[hermetic-platform post] still
apply verbatim.

That is the promise kept: one download, and any document. The next post
opens the package format and shows you every part in detail.
