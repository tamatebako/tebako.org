Real applications rarely live on one runtime. A Ruby tool shells out
to a Java converter, rasterizes a figure with Inkscape, or leans on a
Python utility. This chapter's subject is composition: how your
packaged application uses those things without your users installing
any of them. We start with the simplest case and add one level at a
time.

_Figure 1 — Three routes out of one packaged process: a spawned runtime, a mounted payload, and a declared host tool._

== Level 1: mount a data slice

The simplest composition is your application plus a directory of files.
Press your app with the slice mounted at a path:

[source,console]
----
$ tebako press -r ./myapp -e bin/myapp -o myapp \
    --image acme-fonts-2.1.0.tfs:/usr/share/fonts/acme
----

When the packaged app runs, it reads fonts from
`/usr/share/fonts/acme` exactly as if they were installed — because
the slice is mounted there, in memory, for the whole process. No files
are copied to disk.

== Level 2: declare a runtime your app can spawn

The next level is machinery: your app runs a command that belongs to
another runtime. You declare it in the payload manifest:

[source,yaml]
----
requires:
  # the runtime this payload boots on
  - kind: language
    engine: ruby
    constraint: "~> 3.3.0"
  # the XSL-FO converter (mn2pdf) and the validator (jing) are java
  - kind: runtime
    engine: java
    implementation: temurin
    constraint: ">= 21, < 26"
    expose: [java]          # the command names this payload surfaces
  # figure rasterization is a mounted toolkit payload
  - kind: toolkit           # isodoc rasterizes SVG figures through
    name: inkscape          # vectory -> inkscape for doc/html output
    constraint: ">= 1.3"
    mount: /opt/inkscape
----

Three entries, three different mechanisms, one rule: everything the
process uses is written down.

== Level 3: press and run it

[source,console]
----
$ tebako press -r ./myapp -e bin/myapp -o myapp
$ ./myapp document.adoc
resolving runtime: ruby >= 3.3, < 5.0 (macos-arm64)
runtime ruby-3.3.7 (cached)
resolving requires: java >= 21, < 26
runtime java-21 (downloaded, verified)
----

When your Ruby code runs `java`, tebako starts the OpenJDK runtime's
own executable with its own environment image, as a child process. The
JVM never sits inside the Ruby process, and it never comes from a host
`PATH` — the `expose: [java]` line is what makes the command exist.

== The three routes, side by side

* *A spawned runtime* (the JVM above) — tebako starts the tool's own
  executable with its own environment image, as a child process. Two
  runtimes, two processes, one declared relationship.
* *A mounted payload* (Inkscape) — a slice mounted at a declared path,
  exactly like the fonts in level 1. Payloads requiring payloads is an
  ordinary declaration, not a special case.
* *A declared host tool* (Python) — some tools are deliberately used
  from the host when present, and the manifest says so. Nothing is
  hidden: an absent tool is a named error, not a mystery.
