== Runtime engines

The manifest declares the engine; tebako resolves it:

[source,yaml]
----
requires:
  - kind: language
    engine: ruby          # or jruby
    constraint: "~> 3.3.0"
----

An MRI runtime and a JRuby runtime are the same two artifacts — an
interpreter executable and an environment image — under the same
constraint grammar. A payload with native extensions pins an ABI line
(`~> 3.3.0`) so that a runtime from the wrong line is a named error at
startup, never a segfault at 2 a.m.

== Native code, compiled once

Gems with C extensions are the classic packaging pain: every user
needs a compiler toolchain, matching headers, and luck. Tebako moves
the compilation to press time, on your machine or your CI:

[source,console]
----
$ tebako press -r ./myapp -e bin/myapp -o dist/myapp \
    --target macos-arm64 --target macos-x86_64 \
    --target linux-gnu-x86_64 --target windows-ucrt-x86_64
----

Each target produces one file with its native gems compiled for that
triplet. What your users download is a prebuilt, SHA-256-verified
binary — no compiler, no headers, no luck. For payloads with no native
code at all, one `universal` file covers every platform.

This is the distribution model in one sentence: *the people who build
a package compile it; the people who use it never do.*

== What you can do now

You can choose a runtime engine declaratively, pin ABI lines for
native payloads, and ship compiled gems as binaries per platform. The
last post shows all of it working at once, on the hardest payload we
ship.
