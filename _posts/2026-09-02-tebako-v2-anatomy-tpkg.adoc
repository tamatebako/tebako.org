== Look at what landed on your machine

Start with the store — everything tebako keeps locally lives under
`~/.tebako`, and you can list it:

[source,console]
----
$ tebako info
tebako      0.15.9
platform    macos-arm64

$ tebako info runtimes
ruby-3.3-3.3.7-macos-arm64
  exe + env image · 142 MB

$ tebako info payloads
metanorma  1.2.3  tfs:github:tebako-packages/metanorma
----

Three kinds of things are listed there, and they are the three parts of
every tebako package:

. *The bootstrap* — the small Rust loader that starts every package. It
  is the executable you actually run: it reads the package trailer,
  finds the runtime, and hands control over. It is under 3 MB.
. *The runtime* — the language interpreter, shipped as two files: the
  interpreter executable and an environment image holding the standard
  library and gems. It downloads once per machine, is verified against
  its published SHA-256, and every package on the machine shares it.
. *Payload slices* — the application, its data, and the tools it needs,
  each a disk image that describes itself with a manifest.

== Take a package apart

`tebako inspect` opens any package and prints what is in it:

[source,console]
----
$ tebako inspect ./myapp
kind        package (trailer present)
slots
  0   payload   dwarfs   157 MB   /
runtime     ruby ~> 3.3.0
trust       unsigned (verified at install, SHA-256 sidecar)
----

Read the lines against the model: the slot is a payload slice stitched
into the file; the runtime line is the reference the bootstrap resolves
on first run; the trust line names what was verified when the artifact
entered the store.

== Carried or shared

Every slice in a package is one of two kinds, and `tebako press` locks
the choice when you build it:

* *Carried* — the slice's bytes are inside the executable you ship. One
  file, everything included; this is what the metanorma package does
  with its application slice.
* *Shared* — the executable names the slice, and it resolves from a
  registry into the machine's store on first use. Runtimes always work
  this way; toolkits like Inkscape can too.

Carry changes where the bytes come from, never what runs: the mounted
result is identical either way.

== Which bytes land on a user's machine

Take the shared-runtime metanorma package for `aarch64-macos` and count:

* The download is *one file* — the bootstrap with the application slice
  carried in a slot. The package tarball is 219 MB; the application
  image inside it is 157 MB (Metanorma plus its full gem closure,
  compressed).
* On first run, the bootstrap resolves the runtime reference and
  downloads the two runtime artifacts for the host, verifies both
  against the published SHA-256 sums, and stores them under
  `~/.tebako/runtimes/`. Every other tebako package on the machine
  shares them.
* Anything else the composition declares — the Inkscape slice, the
  OpenJDK runtime from chapter 3 — resolves the same way: fetch once,
  verify, store, share.

Nothing compiles on the user's machine, ever. Prebuilt artifacts flow
down from the factories; the only audience that needs a compiler is the
one building tebako itself.

== The trailer

The whole composition is recorded in a 166-byte trailer plus slot
records at the end of an otherwise ordinary file. That is why a tebako
package stays an ordinary file: you can `curl` it, `chmod` it, ship it
in a tarball, notarize it, or hardlink it into a Chocolatey package —
which is exactly how `fontist.exe` reaches a Windows user's PATH.
