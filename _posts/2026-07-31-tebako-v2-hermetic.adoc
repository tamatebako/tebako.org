= Tebako v2 — the hermetic portable-runtime platform

Tebako v2 is here, and it comes with a proof rather than a promise.

== The proof: a real document, an empty PATH

This week we ran the harshest end-to-end test we could devise. One
command, on an ordinary macOS machine, with *every* host tool made
unreachable:

[source,console]
----
$ PATH= metanorma compile site.adoc
----

`PATH=` is not a typo. The environment carried no `java`, no
`inkscape`, no system toolchain at all. Out came a valid PDF 1.7 — a
real ISO-standard document, complete with a rasterized figure, embedded
fonts, and the full XSL-FO conversion pipeline — byte-for-byte the same
size as the host-built original.

Everything that produced that document came out of three disk images
mounted inside the process, plus one downloaded runtime:

* the *metanorma payload* — the complete Metanorma 1.16.9 application
  with 260 gems, as a single `.tfs` image;
* the *inkscape payload* — Inkscape 1.4.3, mounted at `/opt/inkscape`,
  rasterizing the figure;
* the *openjdk payload* — a Temurin 21 JRE, mounted at `/opt/openjdk`,
  running jing validation and mn2pdf;
* the *ruby runtime* — a patched Ruby 3.3.7, two artifacts (an
  interpreter executable and its environment image), downloaded once
  and shared by every tebako package on the machine.

No Homebrew. No `apt`. No "works on my machine." A user who has never
heard of Java or Inkscape gets the same bytes.

== What Tebako v2 is

Tebako is a *portable-application platform*: package an application
once, run it anywhere — as a single transparent executable your users
never think about, or as a managed, versioned payload with shared
runtimes.

A tebako package is a composition of independently distributable parts:

. **The bootstrap** — a small Rust loader (under 3 MB, size-gated in
  CI). It reads the package trailer, resolves the runtime, verifies it,
  and hands off.
. **The runtime** — two artifacts: the interpreter executable and its
  environment image (`lib/ruby`, gems, everything the load paths
  expect). Downloaded once per machine into `~/.tebako`, SHA-256
  verified, *mounted — never extracted*.
. **Payload slices** — bare `.tfs` images: your app, your data, your
  native tools. Self-describing via an in-image manifest
  (`/__tpkg__/manifest.yaml`).

Slices *co-mount* in one process. An application declares what it needs
— a runtime, a toolkit like Inkscape or a JRE, a data slice — and the
dispatcher mounts each at its declared path. One payload can require
another at a mount point; the dependency is declarative, versioned, and
platform-aware.

Two ways to consume the same packages:

* **Standalone**: the bootstrap and the slices stitched into one
  executable (fat) or referenced from it (lean). Your users download a
  file and run it. The runtime downloads on first run, then it is
  shared.
* **Managed**: `tebako install` from a registry, shims on `PATH`, a
  machine-wide store with content-addressed, trust-anchored artifacts.
  This is the flow that produced the empty-PATH PDF.

== What had to be invented to get here

Running *binaries that live inside disk images* — a JVM included — took
a chain of new machinery, all of it in Rust:

* **The spawn hook.** Every patched Ruby runtime mediates process
  spawning: an exec target held by the mounts is materialized to a host
  cache and executed there, with the preload shim and the current
  mounts injected into the child's environment.
* **Dependency-closure extraction.** The platform loader (dyld, ld.so)
  probes for shared libraries with raw syscalls that no userland hook
  can serve. So `dlmap2file` now parses the Mach-O/ELF dependency
  closure of anything it materializes — rpaths, `@executable_path`,
  `$ORIGIN` — and extracts every in-image library ahead of exec. The
  JVM's hundred-odd dylibs land in place before it starts.
* **The preload shim.** Spawned children re-enter the namespace through
  `DYLD_INSERT_LIBRARIES`/`LD_PRELOAD` plus the mount table — including
  an `fopen` interposition (the JVM's config reads bypass libc `open`
  entirely) and an ABI trampoline for Darwin's stack-passed variadic
  arguments.
* **Zero-runtime payloads.** Native tools — `hello`, Inkscape, a JRE —
  need no interpreter. `tebako install` materializes their executables
  into the store; the shim executes them directly. A whole class of
  software is now a first-class tebako citizen.

== Seven platforms, one payload model

Everything above publishes per platform, and the matrix is honest
about its floors:

[cols="1,2",options="header"]
|===
| Platform | Notes

| `aarch64-macos`, `x86_64-macos`
| Deployment target pinned at macOS 11.0

| `x86_64-linux-gnu`, `aarch64-linux-gnu`
| Built on Ubuntu 20.04 (glibc 2.31); runs there and newer

| `x86_64-linux-musl`, `aarch64-linux-musl`
| Fully static — the universal Linux artifacts, no floor

| `x86_64-windows-ucrt`
| Windows 10 / Server 2016 and newer, runtimes statically linked
|===

An `aarch64-windows-ucrt` leg is reserved but not yet built. Pure-language
payloads ship once as `universal` and run on all seven; only payloads
with native code multiply across the matrix.

== Using it

[source,console]
----
# install tebako (prebuilt, per platform)
brew install tamatebako/tap/tebako

# point at a payload registry and install
tebako add-registry tfs:github:tebako-packages/metanorma
tebako install metanorma

# it's on PATH now — the runtime downloads on first run
metanorma compile site.adoc
----

[source,console]
----
# native toolkits are zero-runtime citizens
tebako add-registry tfs:github:tebako-packages/hello
tebako install hello
hello            # Hello, world!
----

Runtimes download once per machine, are verified against their
published SHA-256, and are shared by every package. Payloads are
byte-identical with what the publisher released. A run never installs
anything; `tebako install` is the explicit verb.

== Migrating from Tebako v1

The C++/CMake era is archived as
https://github.com/tamatebako/tebako-v1[tebako-v1] and will not receive
new development. What changes for you:

* **The gem is replaced by the Rust CLI.** `tebako press` stays
  `tebako press` — now a prebuilt binary, no CMake, no compilers on
  your machine; trailer-level surgery lives in `tebako-pkg`, and image
  work in `tfs`.
* **Images are v2-only.** v1 embedded images do not load in v2; press
  fresh payloads with the new tooling. The `.tfs` format is the
  dwarfs-t image (FlatBuffers metadata — upstream DwarFS cannot read
  it).
* **The runtime model changed.** v1 merged environment+application into
  one image. v2 separates them: a shared runtime (executable + env
  image) and bare payload slices. Leaner, cacheable, composable.
* **Patches live per Ruby version** in
  https://github.com/tamatebako/ruby[tamatebako/ruby], applied and
  released as patched-source tarballs; the runtime factory builds
  runtimes from them. Your `RUBY VERSION` pin maps to a runtime
  constraint like `~> 3.3.0` in the payload manifest.

== Tags

The v2 line tags alongside this announcement:

* `tamatebako/tebako` — the Rust product (bootstrap, shim, driver,
  tfs, tpkg, CLI): *v2.0.0*
* `tamatebako/tebako-runtime-ruby` — the runtime factory: *0.16.0*
* `tamatebako/ruby` — the patch factory (36 Ruby versions, 3.1–4.0):
  patched-source releases
* `tebako-runtime` — the in-runtime adapter gem: *0.8.0* on RubyGems

More runtimes (Python next), more payload feedstocks, and the Windows
legs come next, in that order.

== The point

"Package once, run anywhere" has been promised before — usually by
tools that quietly require a machine that looks like the build machine.
The empty-PATH compile is our answer: nothing on the host mattered, so
nothing on the host can break it.
