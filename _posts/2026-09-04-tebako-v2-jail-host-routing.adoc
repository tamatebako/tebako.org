chapter's subject is the boundary between a running package and the
host: what it may touch, who decides, and how you find out. Every step
is a command.

== Level 1: the default is nothing

Run a package with the jail closed and watch:

[source,console]
----
$ tebako run ./myapp --jail deny -- --help
tebako: jail: denied host read: $HOME/.config/myapp/settings.yml (exit 73)
----

Read-only by default: every file access a payload makes flows through
one choke point inside tebako, and with `--jail deny` the answer to
each one is no. The denial is named — the path, the operation, the exit
code — never a crash.

== Level 2: grant what is needed

The package declares what it needs; the run binds it. A grant looks
like this:

[source,yaml]
----
needs:
  host:
    - path: $HOME/.fontist        # symbolic atom, resolved per user
      access: rw                  # ro | rw
      when: [macos]               # optional platform filter
      why: "fontist caches and resolves fonts here"   # MANDATORY
----

The `why` is mandatory grammar, not a style preference: a declaration
that cannot explain itself does not parse. Symbolic paths (`$HOME`,
`$TMPDIR`, `$CWD`, the store itself) resolve at bind time, per user,
per run. Everything not granted stays invisible.

== Level 3: don't guess — record

Writing the grants by hand means guessing. Record mode runs the package
for real and drafts them for you:

[source,console]
----
$ TEBAKO_JAIL=record tebako run ./myapp -- build
$ tfs needs --from-journal ~/.tebako/journal.log
needs:
  host:
    - path: $HOME/.fontist
      access: rw
      why: ""
----

The journal holds every host access the run attempted; the draft lists
them as grants. You review it, adjust `ro` and `rw`, fill in every
`why`, and bind it — the acceptance path and the discovery path are the
same run.

== One declaration, every platform

The declaration is identical everywhere; only the enforcement differs.
On Linux and macOS the choke point sits in the filesystem layer. On
Windows, where no such interposition exists, enforcement moves to the
spawn tier — executables are materialized into a cache and started with
rewritten arguments, under the same policy computed from the same
declarations. And trust is settled before any of this: artifacts are
verified when they enter the store, never re-verified per run, so a
run with a jail is as fast as a run without one.

== What you can do now

You can take any package and decide, precisely, what it may touch —
and produce the grants from a real run instead of a guess. One thing
remains: building a package of your own. That is the last chapter.
